## ۳. روال هر جلسه

1. فایل‌های بند ۲ را بخوان.
2. «⏭️ قدم بعدی» در `PLAN.md` را انجام بده — بدون پرسیدن، **مگر** کنارش ⛔ باشد یا کار یک قابلیت/تصمیم تازه باشد؛ آن‌وقت اول با مثال ساده بپرس.
3. **کلمه‌ها:** مستقیم روی main. فقط Dart SDK لازم است (`source tool/dart_umgebung.sh`)؛ تحلیل و تست را GitHub قبل از انتشار اجرا می‌کند.
4. **تغییر کد** (`lib/`، `test/`، `pubspec`، `web/`، `.github/`): اول روی شاخه‌ی جدا ⇒ روال `pruefen.yml` سبز ⇒ بعد main. اگر لازم شد Flutter کامل در کانتینر دانلود می‌شود (دستور در `docs/WORTROUTINE.md`، مرحله‌ی ۲).
5. هر push روی main یعنی انتشار روی GitHub Pages برای کاربران واقعی.
6. **Actions:** در دور کلمه قبل از push بعدی چک شود؛ در تغییر کد بعد از هر push؛ **آخر هر جلسه همیشه یک اجرای سبز.**
7. هیچ راه‌حل موقت یا آزمایشی؛ از اول راه درست و ماندگار.
8. جواب به Lukas همیشه فارسی، کوتاه و ساده؛ هر جا لازم بود با مثال.

## ۵. قاعده‌های ثابت کلمه‌ها (فقط با تصمیم صریح Lukas عوض می‌شوند)

1. پرامپت هرگز اطلاعات ظاهری (رنگ، آیکون، شکل) تولید نمی‌کند؛ این‌ها همیشه در کد محاسبه می‌شوند، نه در JSON کلمه.
2. برای زبان‌ها هرگز کارت جدا ساخته نمی‌شود: فارسی و انگلیسی همیشه در **یک** کارت‌اند. (این قاعده درباره‌ی زبان است؛ این‌که یک نوشتار با چند معنی چند کارت می‌گیرد یا نه، موضوع «چهار حالت» است ⇒ `docs/zukunft/VIER_FAELLE.md`.)
3. اگر داده برای تعیین شکل درست کافی نیست (مثلاً trennbar نامشخص): نماد نباشد بهتر از نماد غلط است. هرگز حدس نزن.
4. رنگ آرتیکل فقط یک منبع دارد: `GrammatikonSpec`. هیچ فایل دیگری رنگ مستقل تعریف نمی‌کند.
5. تنها منبع ساخت کارت: `old files Lukasalmani/Wort prompt`. تنها منبع کنترل و id: `vokab_schema.dart`.
6. id هیچ کارت منتشرشده‌ای عوض یا حذف نمی‌شود (نگهبان L.1a).

## ۶. وقتی چیزی خراب شد

| وضعیت | کار |
|---|---|
| Actions قرمز به خاطر تغییر ما | فوراً درست کن؛ تا سبز نشده کار تازه شروع نکن. |
| Actions قرمز به خاطر خود GitHub (Timeout در deploy-pages، دانلود خراب) | توکن اجازه‌ی «اجرای دوباره» ندارد ⇒ با کامیت بعدی (یا یک کامیت سند) دوباره اجرا می‌شود. در `docs/VERLAUF.md` ثبت کن. |
| نسخه‌ی منتشرشده اشتباه کار می‌کند | کامیت‌های همان تغییر را با `git revert` برگردان و push کن؛ بعد علت را پیدا کن. هرگز `force-push`، هرگز بازنویسی تاریخچه. |
| دو چت هم‌زمان روی ریپو | قبل از هر push اول `git pull --rebase`؛ اگر تداخل بود، دست نگه دار و از Lukas بپرس. |
| شک درباره‌ی داده‌ی کاربر | هیچ تغییری بدون تست نگهبان و بدون تأیید Lukas. پیشرفت لایتنر هرگز نباید از دست برود. |
